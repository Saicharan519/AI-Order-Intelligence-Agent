# Variance and model comparison (M10)

Configuration D (views, full glossary, validator, up to two repairs; prompt `sqlgen-v1`) on the frozen 20-item test split; 18 items are answerable SQL questions (the 2 out-of-scope items are routed, not scored here). Generated by `eval/model_comparison.py` from `eval/results/`.

## Variance (T-10.2): three deepseek-flash runs

Correct: 15, 16, 15 of 18, so accuracy 83% to 89% (mean 85.2%). Run 1 is the M5 headline run (its first request was served from configuration C's cache); runs 2 and 3 bypassed the response cache, so each made fresh model calls. Only one item changed between runs (`trap_14`, the deliberately ambiguous "best seller" question); the other 17 had the same outcome in all three runs. With 18 items, one item is 5.6 points, so the 95% interval of any single run (shown below) is far wider than the run-to-run spread.

### Items where the runs disagree

| Item | flash run 1 | flash run 2 | flash run 3 | v4-pro | Gemini |
|---|---|---|---|---|---|
| `lookup_03` | wrong | wrong | wrong | ok | wrong |
| `agg_11` | ok | ok | ok | wrong | ok |
| `trend_08` | wrong | wrong | wrong | wrong | wrong |
| `trap_14` | wrong | ok | wrong | ok | ok |
| `ambig_06` | ok | ok | ok | wrong | ok |

Why (from the stored SQL):
- `trend_08` (orders per payment type): wrong for every model. The `payments` view keeps one row per order with a primary payment type, so per-type counts of payment rows are not available through the views; a known trade-off of the fan-out protection (M5).
- `lookup_03` (delivery date of one order): deepseek-flash and Gemini return the delivery timestamp instead of the date. The value is right; the comparer requires the date column, so this is partly scorer strictness.
- `agg_11` (average order value 2017): deepseek-v4-pro divides revenue of all orders by the number of sales, so canceled orders inflate the numerator: a real error.
- `ambig_06` ("late-delivery rate recently"): deepseek-v4-pro chose a different recent window than the reference; defensible for an ambiguous question, scored wrong.
- `trap_14` ("best seller"): one deepseek-flash run returned a top-10 list instead of a single seller.

## Investigations: deepseek-v4-pro on five cases

| Case | deepseek-flash (M7) | deepseek-v4-pro |
|---|---|---|
| `inv_late_01` | elevated, driver carrier_transit | elevated, driver carrier_transit |
| `inv_late_04` | elevated, driver carrier_transit | elevated, driver carrier_transit |
| `inv_rev_01` | elevated, driver late_delivery | elevated, driver late_delivery |
| `inv_neg_01` | nothing_notable, driver none | nothing_notable, driver none |
| `inv_none_01` | refuse (correct) | wrong route (investigate) |

Cost of these five: deepseek-v4-pro $0.0073; deepseek-flash $0.0023 (M7, partly cached).

`inv_none_01` ("Why did revenue fall in June 2018?") has no applicable playbook. deepseek-flash refused it; deepseek-v4-pro routed it to the low-review playbook and answered about review scores, which does not answer the question. Every number was grounded and nothing unsafe ran, but the answer is wrong. It exposes a gap: no code check ties the chosen playbook to the topic of the question (recorded as a known limitation; a topic check in the router is a candidate fix).

## Decision

deepseek-flash stays the primary model. deepseek-v4-pro was not more accurate on the test split (15/18, the same as two of the three flash runs), cost about 4x as much per item, was slower, and misrouted one investigation that flash handled. The Gemini free tier matched flash on SQL accuracy (16/18) at no cost, but its rate limit (12 requests per minute, 450 per day) makes it unsuitable as the primary model for a demo; it remains the optional second provider (Q-10). With 18 items, none of these differences is statistically significant: the intervals overlap almost completely.
